1What is Docker, and why do we need it?

Imagine you spend days setting up your app on your laptop — installing Python, PostgreSQL, Node.js, all the right versions. Then a friend tries to run it and nothing works because their machine is set up differently. Docker solves this.

🚢 The Shipping Container Analogy

Before shipping containers were invented, every ship had to figure out how to load each item differently — furniture, bananas, machinery. It was chaos. Then someone invented the standardized shipping container: one box, same size, fits any ship, any truck, any crane.

Docker does the same thing for software. You put your app inside a container — it has everything it needs (Python, libraries, configs) packed inside. That container runs identically on your laptop, your teammate's Mac, or a server in the cloud.

The 3 core concepts you need to know

📦
Image
A recipe / blueprint. Like an ISO file — a snapshot of the app and everything it needs. Read-only. Built once, used many times.
🏃
Container
A running instance of an image. Like a house built from blueprints. You can start, stop, and delete containers freely.
💾
Volume
Persistent storage that survives container restarts. Like an external hard drive plugged into the container.
💡

Key insight: An Image is the recipe. A Container is the meal. You can cook (run) many meals from the same recipe. If a meal goes wrong, throw it away and cook a fresh one — the recipe is untouched.

What is Docker Compose?

HarvestGuard isn't one app — it's four apps that need to work together (database, cache, backend API, frontend). Docker Compose lets you define and start all of them with a single command: docker compose up.

Think of it as a conductor that starts the whole orchestra at once, in the right order, making sure everyone can hear each other.

2Your 4 services — what each one does

Open your docker-compose.yml. You have 4 services. Here's what each one is, why HarvestGuard needs it, and what would break without it.

🐘
PostgreSQL + PostGIS
Database

Stores all your data permanently: countries, NDVI readings, rainfall history, risk scores, alerts. PostGIS is an extension that adds geospatial superpowers — it understands latitude, longitude, and country shapes.

⚡
Redis
Cache

An ultra-fast in-memory store. Used for caching NASA and WFP API responses so you don't hammer external APIs on every request. Like a notepad for answers you already looked up.

🐍
FastAPI (Python)
Backend

The brain of HarvestGuard. Fetches satellite data, runs risk scoring, calls Ollama for AI assessments, and serves all the data to the frontend via REST API + streaming.

⚛️
React + Nginx
Frontend

The interactive world map you see in your browser. Nginx is a tiny web server that serves the React app files and also forwards API requests to FastAPI (so you only need one address).

Why can't they all be one app?

🏢 The Office Building Analogy

Think of HarvestGuard as an office building. The database (PostgreSQL) is the filing room — stores everything permanently. Redis is the receptionist's sticky notes — quick lookups for common questions. The API (FastAPI) is the actual employees doing the work. The frontend (React) is the lobby — what visitors (your browser) interact with.

You wouldn't hire one person to do all four jobs simultaneously. Each service does one thing well, and they talk to each other.

3Your docker-compose.yml — line by line

Let's walk through every line of your actual config file and explain what it does in plain English.

📄 docker-compose.yml
services:                       # "Here are the apps I want to run"

  postgres:                       # Name we give this service
    image: postgis/postgis:16-3.4  # Use this pre-built image from Docker Hub
    environment:                   # Environment variables (like settings)
      POSTGRES_USER: harvestguard   # Create a DB user named harvestguard
      POSTGRES_PASSWORD: secret     # With this password
      POSTGRES_DB: harvestguard     # Create a database named harvestguard
    volumes:
      - postgres_data:/var/lib/postgresql/data  # Save DB files here permanently
    ports:
      - "5432:5432"                  # Expose port 5432 (so you can connect externally)
    healthcheck:                   # Tells Docker "is this service ready yet?"
      test: ["CMD-SHELL", "pg_isready -U harvestguard"]

  redis:
    image: redis:7-alpine          # Alpine = tiny version (5MB vs 100MB)
    ports:
      - "6379:6379"
📖

About ports "5432:5432": This is "YOUR_COMPUTER:CONTAINER". Port 5432 inside the container is mapped to port 5432 on your laptop. So localhost:5432 on your machine reaches the database inside Docker. If you wrote "9999:5432", you'd connect via localhost:9999 instead.

📄 docker-compose.yml (continued)
  api:
    build:
      context: ./backend            # BUILD an image from the ./backend folder
      dockerfile: Dockerfile        # Using these instructions
    env_file: .env                 # Load secrets from your .env file
    environment:
      DATABASE_URL: postgresql+asyncpg://harvestguard:secret@postgres:5432/harvestguard
                                     # "postgres" = the service name above (auto DNS!)
    ports:
      - "8000:8000"                  # API available at localhost:8000
    depends_on:
      postgres:
        condition: service_healthy   # Wait for postgres to be ready FIRST
    command: uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

  frontend:
    build:
      context: ./frontend
    ports:
      - "3000:80"                    # Your port 3000 → nginx port 80 inside
    depends_on:
      - api                          # Start after api is running

volumes:
  postgres_data:                   # Named volume — Docker manages this storage
                                   # Data survives "docker compose down"

The magic of service name DNS

Inside Docker's network, services find each other by name. Look at your DATABASE_URL:

# This URL in your API container:
DATABASE_URL=postgresql+asyncpg://harvestguard:secret@postgres:5432/harvestguard
#                                  user        password  ↑hostname  port
#                                                        = service name in compose!

The word postgres in that URL isn't a real hostname you set up — Docker automatically makes it resolve to the postgres container. Same with redis. They just work.

Why Ollama is special (outside Docker)

Ollama runs on your Windows machine, not inside Docker. So the API container can't use localhost to reach it — from inside a container, localhost means the container itself, not your PC.

# WRONG — "localhost" inside Docker = the container itself
LOCAL_LLM_BASE_URL=http://localhost:11434/v1

# CORRECT — "host.docker.internal" = your actual Windows/Mac machine
LOCAL_LLM_BASE_URL=http://host.docker.internal:11434/v1
⚠️

This is the #1 Docker gotcha on Windows/Mac. Always use host.docker.internal when a Docker container needs to reach a service running on your actual machine (like Ollama, a local dev server, etc.).

5What is a Dockerfile?

Some services use a pre-built image from the internet (like redis:7-alpine). Others — your API and frontend — get built from a Dockerfile: a recipe that tells Docker how to create a custom image for your specific app.

👨‍🍳 Recipe analogy

A Dockerfile is like a cooking recipe. Each line is an instruction: "Start with this base ingredient, add these tools, copy in these files, run this command to install dependencies, then set the default action when you serve it."

Your backend Dockerfile

📄 backend/Dockerfile
FROM python:3.11-slim
# Start from an official Python 3.11 image (pre-built by Docker)
# "slim" = stripped down version — smaller, faster to download

WORKDIR /app
# All following commands run from the /app folder inside the container

RUN apt-get update && apt-get install -y \
    gdal-bin libgdal-dev libgeos-dev gcc
# Install system libraries that geopandas and rasterio need
# (These handle the geospatial/satellite data processing)

COPY pyproject.toml .
RUN pip install --no-cache-dir -e .
# Copy your dependency list, then install all Python packages
# Separated from copying your code so Docker can CACHE this layer
# (If you only change code, Docker reuses the installed packages)

COPY app/ ./app/
# Copy your actual Python source code into the container

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
# Default command when the container starts = run the FastAPI server

The caching trick (why order matters in Dockerfiles)

Docker builds images in layers. Each instruction creates a layer, and Docker caches layers. If a layer hasn't changed, Docker reuses it instantly instead of rebuilding.

# SMART ORDER (dependencies before code):
COPY pyproject.toml .    ← layer 1: rarely changes → cached most of the time
RUN pip install ...     ← layer 2: rarely changes → cached (saves minutes!)
COPY app/ ./app/        ← layer 3: changes often  → rebuilt, but fast

# WRONG ORDER (code before dependencies):
COPY app/ ./app/        ← changes every save → invalidates ALL layers below
RUN pip install ...     ← re-runs every time  → wastes 2-5 minutes every build!
💡

Rule of thumb: Put things that change rarely at the top of your Dockerfile, things that change often at the bottom. This keeps builds fast.

6Volumes — keeping your data safe

Containers are designed to be disposable. If you delete a container, everything inside it vanishes. But you don't want your database wiped every time you restart. That's what volumes are for.

🔌 External hard drive analogy

Imagine your container is a laptop. If you throw the laptop away and get a new one, everything on the internal drive is gone. But if your data was saved to an external hard drive (a volume), you just plug that drive into the new laptop and all your data is there.

📄 docker-compose.yml
postgres:
  volumes:
    - postgres_data:/var/lib/postgresql/data
    #   ↑ volume name      ↑ path inside the container where Postgres saves data

volumes:
  postgres_data:     # Docker creates and manages this storage on your machine

Three scenarios with volumes

Action What happens to your data
docker compose down ✅ Data is safe. Volume persists. Next up picks right up.
docker compose restart ✅ Data is safe. Container restarts, volume still attached.
docker compose down -v ⚠️ Data is DELETED. The -v flag removes volumes. Use to start completely fresh.
⚠️

Never run docker compose down -v unless you want to wipe your database completely and start over. The plain docker compose down is safe.

7Health checks & startup order

Your services start simultaneously by default — but your API needs the database to be actually ready before connecting. Health checks solve this.

🍳 Restaurant analogy

Imagine a restaurant where the waiter (API) needs the kitchen (database) ready before they can take orders. Without health checks, the waiter starts walking around as soon as they arrive — even if the kitchen is still warming up and the chef isn't ready. healthcheck + depends_on: condition: service_healthy makes the waiter wait in the back until the kitchen actually signals "we're ready!"

📄 docker-compose.yml
postgres:
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U harvestguard"]
    #    ↑ Run this command inside the container every 10s
    #      pg_isready exits 0 (success) when Postgres is accepting connections
    interval: 10s   # Check every 10 seconds
    timeout: 5s     # Give up if no response in 5 seconds
    retries: 5      # Try 5 times before marking as unhealthy

api:
  depends_on:
    postgres:
      condition: service_healthy  # Don't start API until postgres passes healthcheck
    redis:
      condition: service_healthy

Startup sequence in your project

1
PostgreSQL + Redis start simultaneously
Docker pulls the images (first time only) and starts both containers
2
Health checks run every 10 seconds
Docker checks if Postgres is accepting connections. Redis does the same with redis-cli ping.
3
FastAPI starts (only after both are healthy)
Creates database tables, seeds 60 countries, starts the scheduler
4
React frontend starts (after API)
Nginx serves the built React app at localhost:3000

8Commands you'll use every day

You don't need to memorize Docker internals — just these commands will cover 95% of what you need.

Starting & stopping

CommandWhat it does
docker compose up --build Start everything, rebuild images first. Use this after changing Python/JS code.
docker compose up Start everything using existing images (faster if nothing changed).
docker compose down Stop and remove containers. Your database data is safe (volume preserved).
docker compose down -v ⚠️ Stop everything AND delete all data. Full reset.
docker compose restart api Restart just the API service without touching others.

Watching what's happening

CommandWhat it does
docker compose logs -f Stream live logs from all services (Ctrl+C to stop).
docker compose logs -f api Stream logs from just the API service.
docker compose ps List all running containers and their status.

Debugging (going inside a container)

CommandWhat it does
docker compose exec api bash Open a terminal shell inside the running API container. Type exit to leave.
docker compose exec postgres psql -U harvestguard Open a PostgreSQL prompt directly in the database. Type \q to leave.

HarvestGuard-specific commands

CommandWhat it does
curl -X POST http://localhost:8000/api/v1/admin/refresh Trigger a fresh pull of WFP + satellite data for all 60 countries.
curl http://localhost:8000/health Check if the API + database are connected and healthy.
curl http://localhost:8000/api/v1/alerts See all active food security alerts in JSON.
💡

Tip: Keep a terminal open running docker compose logs -f api while developing. You'll see every request, error, and data refresh in real time — much easier than guessing what's happening.

9The full picture — what happens when you visit localhost:3000

Let's trace one real request end-to-end: you click on Ethiopia on the map.

Step 1: Browser
→ GET http://localhost:3000/api/v1/regions/ETH

Step 2: Nginx (frontend container, port 3000)
→ Sees "/api/" path → proxies to http://api:8000/api/v1/regions/ETH
(uses Docker's internal DNS to find the "api" container)

Step 3: FastAPI (api container, port 8000)
→ Checks Redis cache: "do I have ETH data from last 10 min?"
→ Cache miss → queries PostgreSQL: "SELECT * FROM countries WHERE iso='ETH'"
→ Gets NDVI history, rainfall data, risk score from DB
→ Returns JSON response

Step 4: You click "Get AI Assessment"
→ Browser opens EventSource to /api/v1/forecast/ETH (SSE stream)
→ FastAPI builds prompt with real NDVI + rainfall data
→ FastAPI calls http://host.docker.internal:11434/v1 (your Ollama)
→ Streams tokens back word by word → appears live in the UI

Why each service is necessary

Remove this serviceWhat breaks
postgresNo data storage. Every restart starts blank. Countries, NDVI readings, alerts — all gone.
redisAPI still works but hits external APIs (WFP, Open-Meteo) on every request — slow and rate-limited.
apiNo data, no AI assessments, no alerts. The frontend shows an empty map.
frontendNo UI. The API still works — you'd interact with it via raw JSON at localhost:8000.
Ollama (on your PC)AI assessments and chat return an error message. Everything else still works.
🎯

The takeaway: Each Docker service is one focused piece of the puzzle. Docker Compose is the glue that starts them all, connects them on a private network, and manages their lifecycle with a single command.
